2. Critical Findings

Critical

C1: Authentication Is Entirely Client-Side — Trivially Bypassable

Evidence: Lines 1020-1035, 1162-1196. The doLogin() function reads users from localStorage, compares simpleHash(password), and sets CURRENT_USER in JavaScript. There is no server, no token, no session verification. Any user can open DevTools and run:

CURRENT_USER = {id:'admin', username:'admin', fullName:'Admin'};
localStorage.setItem('matokeo_session', JSON.stringify(CURRENT_USER));
location.reload();

Impact: Complete authentication bypass. Anyone with browser access can impersonate any user and access all student data stored in that user's localStorage namespace.

Root Cause: GitHub Pages is a static host — it cannot perform server-side authentication. The entire auth model is fundamentally incompatible with any real security requirement.

Critical

C2: Password "Hashing" Uses Non-Cryptographic Algorithms (djb2 + sdbm)

Evidence: Lines 1021-1035. The simpleHash() function combines djb2 and sdbm — both are non-cryptographic hash functions designed for hash tables, not security. They are fast, have known collision properties, and can be reversed via brute force in milliseconds.

function simpleHash(str) {
  let h = 0;
  for (let i = 0; i < str.length; i++) {
    h = ((h << 5) - h) + str.charCodeAt(i);  // djb2
    h = h & h;
  }
  // ... sdbm pass ...
  return 'h_' + Math.abs(h).toString(36) + '_' + Math.abs(h2).toString(36);
}

Impact: Passwords are effectively stored in plaintext. The hash output space is only ~64 bits (two 32-bit ints), and the algorithm has no salt, no stretching, and no memory-hardness. Rainbow tables or brute force can crack any 4-character password instantly.

Comment in code admits this: // Simple hash (not cryptographic, but sufficient for local password storage) — but even for local storage, this provides no real protection against a determined user.

Critical

C3: No Firebase Authentication — Firestore Has No Identity to Enforce Rules Against

Evidence: Lines 1104-1160. Firebase is initialized with user-provided config (from a textarea), but Firebase Auth is never used. The app only uses Firestore's collection('users').doc(CURRENT_USER.id) path, where CURRENT_USER.id is a client-generated string like 'u_' + Date.now().toString(36).

Impact: Firestore security rules cannot distinguish between users because there is no Firebase Auth UID. Any Firestore rules would have to either (a) allow all reads/writes (insecure) or (b) be impossible to write correctly without Auth. Currently, no Firestore security rules exist — the project has zero server-side authorization.

Critical

C4: Firestore Security Rules Missing — All Data Open to Anyone With Config

Evidence: The Firebase config is entered by the user via a textarea (line 967). Once connected, the app reads/writes to /users/{userId}/data/students with no authentication. Anyone who obtains the Firebase config (stored in localStorage, visible in DevTools) can read/write ALL users' data directly via the Firestore API or Firebase Console.

Impact: Complete data exposure. Student records, names, classes, and scores can be read, modified, or deleted by anyone with the Firebase project config. There is no access control whatsoever at the database level.

Critical

C5: Default Credentials Published in README

Evidence: README.md line 27: Ingia: username `zarem` / password `zarem`

Impact: The default admin account credentials are publicly documented. Combined with C1-C4, this means anyone who finds the repository can immediately access the migrated data of the original user.

Critical

C6: All Users Share the Same Browser — No Multi-Tenant Isolation

Evidence: Lines 1037-1047. All user accounts are stored in a single matokeo_users array in localStorage. Data is namespaced by user ID, but any JavaScript running on the page can read all users' data by iterating the matokeo_users array and reading each matokeo_v2_{id}_data key.

Impact: There is no isolation between users on the same browser. A logged-in user can access any other user's student records by simply reading localStorage keys. This violates the fundamental principle of multi-tenant data isolation.

3. High Findings

High

H1: Session Token Stored in localStorage — Vulnerable to XSS

Evidence: Line 1177. localStorage.setItem('matokeo_session', ...). If any XSS vector exists (and several CDN scripts load without SRI hashes), an attacker can steal the session.

Impact: Session hijacking via XSS. Combined with C1, the session is trivially forgeable anyway, but this compounds the risk.

High

H2: CDN Dependencies Loaded Without Subresource Integrity (SRI) Hashes

Evidence: Lines 15-21. All external scripts (Chart.js, jsPDF, SheetJS, Firebase) are loaded via cdn.jsdelivr.net without integrity or crossorigin attributes.

<script src="https://cdn.jsdelivr.net/npm/chart.js@4.4.0/dist/chart.umd.min.js"></script>
<script src="https://www.gstatic.com/firebasejs/10.7.1/firebase-app-compat.js"></script>

Impact: If the CDN is compromised (or jsdelivr has a supply-chain incident), malicious code could be injected into every user's browser. This is especially dangerous because the app handles student data.

High

H3: No Role-Based Access Control (RBAC)

Evidence: The user model (line 1246) has only {id, fullName, username, password, createdAt}. There is no role field. All users have identical permissions — there is no distinction between admin, teacher, or viewer.

Impact: Any registered user can perform all operations including deleting all data (confirmClearAll()), changing settings, and accessing all student records.

High

H4: Backup Import Silently Overwrites Existing Records

Evidence: Lines 2003-2006. When importing a JSON backup, if a student with the same name+class+term exists, the existing record is overwritten without confirmation:

if (existing !== -1) { DATA[existing] = {...DATA[existing], ...bs, id: DATA[existing].id}; updated++; }

Impact: Data loss. A corrupted or outdated backup can silently overwrite current data with no warning, no diff preview, and no undo.

High

H5: No Content Security Policy (CSP)

Evidence: No CSP meta tag or header exists. GitHub Pages does not set a restrictive CSP by default for user content.

Impact: Without CSP, any XSS vulnerability (including via imported Excel data or JSON backups) can execute arbitrary JavaScript, steal data, or redirect users.

4. Medium Findings

Medium

M1: Excel Import Silently Converts Invalid Scores to null

Evidence: Lines 1717-1720. When importing Excel data, invalid scores (negative, >100, non-numeric) are silently set to null instead of reporting the error:

if (n !== null && (isNaN(n) || n < 0 || n > 100)) { scores[sub.key] = null; }

Impact: Data corruption. A teacher importing an Excel file with a typo (e.g., "85" entered as "850") will silently lose that score. The import preview shows the converted value but doesn't flag it as an error.

Medium

M2: Position Calculation Doesn't Handle Ties

Evidence: Lines 1453-1458. computePositions() sorts students by average and assigns positions by array index. Two students with identical averages get different positions (e.g., 3rd and 4th instead of both being 3rd).

sorted.forEach((s, i) => { posMap[s.id] = i + 1; });

Impact: Incorrect rankings. In Tanzanian schools, tied scores should receive the same position (e.g., 1, 2, 2, 4). This affects report cards and the dashboard.

Medium

M3: Pass Rate Threshold Inconsistent With Grade Boundaries

Evidence: Line 1593 uses avg(s) >= 40 for pass rate calculation. But the grade function (line 1438) defines F as < 30 and D as 30-44. So a student with average 35 gets grade D but is counted as "failing" in the pass rate.

Impact: Misleading statistics. The dashboard pass rate doesn't match the grading system. This could confuse teachers and administrators.

Medium

M4: Average Excludes Null Scores — Inflates Averages for Incomplete Records

Evidence: Lines 1446-1448. The avg() function filters out null/undefined scores before computing the mean. A student with only 1 subject scored (e.g., 90 in Hisabati, all others null) gets average = 90, same as a student who scored 90 in all 6 subjects.

Impact: Unfair rankings. Students with incomplete records can rank higher than students with complete but lower scores. This is especially problematic when importing data with missing columns.

Medium

M5: No Error Handling for Failed Firestore Writes

Evidence: Lines 1080-1083. Cloud save failures are caught but only logged with console.warn. The user sees no indication that their data failed to sync:

catch(e) { console.warn('Cloud save failed:', e); }

Impact: Data loss risk. A teacher might believe their data is synced to the cloud when it actually isn't. If they switch devices, their data appears missing.

Medium

M6: No Duplicate Detection in Excel Import — ID Collision Possible

Evidence: Line 1722. Each imported row gets a new ID: Date.now().toString(36) + Math.random().toString(36).slice(2,6). If two rows are processed in the same millisecond, they could theoretically get the same timestamp prefix. More importantly, the duplicate check (line 1744) only compares name+class+term — it doesn't check if the imported student has a different ID but same identity.

Impact: Potential duplicate records or silent data merging.

Impact: Difficult to maintain, test, or review. Any change requires navigating the entire file. Makes automated testing impractical.

Low

Evidence: No test files, no test framework, no package.json. Zero test coverage.

Impact: Regressions can only be caught manually. Calculations, imports, and exports have no verification.

Low

L3: Session Timer Resets on Any Mouse Movement — Not a Real Timeout

Evidence: Line 1981. resetSessionTimer() resets the 30-minute countdown on any click, keydown, mousemove, or touchstart. But it resets to exactly 30 minutes regardless of how much time was left. The timer also continues counting down in the background even when the user is active — it only resets the counter, not pauses it.

Impact: The session timeout provides a false sense of security. It's a UX feature, not a security control.

Low

L4: PWA Manifest Uses External Placeholder Icon

Evidence: Line 12. The PWA manifest references via.placeholder.com/192/66bb6a/ffffff?text=MP as the app icon. This external service could go down or serve malicious content.

Impact: PWA install may fail or display incorrectly. Minor reliability issue.

9. Required Actions From You

Before I proceed to Phase 2 (Planning) and Phase 3 (Implementation), I need your input on these decisions:

1. Authentication Strategy: Since this is a static site on GitHub Pages, there is no server for traditional auth. Options:

  • A) Firebase Authentication — Add Firebase Auth (email/password or Google sign-in). This gives real server-side auth with UID-based Firestore rules. Free tier is sufficient. (Recommended)
  • B) Third-party auth service — Clerk, Auth0, or Supabase Auth. More features but adds a dependency.
  • C) Keep client-side auth but document it as insecure — Only suitable if this is a personal tool with no real security needs.

2. Grading Rules: The current code uses: A(75-100), B(60-74), C(45-59), D(30-44), F(0-29). Is this the correct Tanzania grading scale you want? Or do you have official rules?

3. Pass Threshold: Should "passing" be >= 30 (grade D or above) or >= 40 (current dashboard logic) or something else?

4. Tie Handling: Should students with identical averages share the same position (e.g., 1, 2, 2, 4)? This is standard in Tanzanian schools.

5. Average Calculation: Should the average divide by total subjects (6) or only by subjects with scores? Currently it divides by non-null count, which inflates averages for incomplete records.

6. User Roles: Do you need role separation (Admin vs Teacher vs Viewer)? Or is a single user type sufficient for now?

7. Firebase Project: Do you already have a Firebase project set up for this? Or should I write setup instructions for you to create one?
